The 4th Coming — Changelog

This changelog summarises every change made split between the Client and the Server.

CLIENT Game client

Rendering & graphics

  • Direct3D 11 backend — Migrated the renderer from DirectDraw to Direct3D 11 behind a new IRenderer abstraction (DDraw7 kept as fallback).
  • DirectDraw removed for good — D3D11 is now the one and only backend (no more d3d11on.txt marker, no DDraw fallback). Sprite pixels live in plain system-memory surfaces (SoftSurface: software blits with colour-key, mirror, stretch, GDI text); ddraw.dll is no longer imported by the executable.
  • World lighting on the GPU — The per-pixel lighting multiply (world × lightmap) and the full-screen 565→RGBA conversion moved from the CPU to a pixel shader — bit-exact same output, including the “full-bright” low-light mode. Render-thread CPU cut by ~55%.
  • D3D11 sprite features — Horizontal mirroring and global per-vertex semi-transparency on the GPU path.
  • x64 build — The client now builds and runs as a 64-bit application.
  • 1080p edge culling fix — NPCs, objects and lights at the screen edges are no longer wrongly culled at 1080p.
  • Login preview fix — Fixed a sprite glitch in the character preview on the login screen.
  • Fullscreen lag fix — Removed a stutter specific to fullscreen mode.

Performance

  • 64 FPS — Fixed-step rendering raised to a clean 64 fps.
  • Algorithmic fixes — Replaced several O(n²) hot paths (object sorting, child lookup, z-ordering) with O(n)/stable approaches.
  • Software alpha blend — Vectorised 565 alpha blending and improved transparency, removing the semi-transparency frame drops.
  • Effect throttling — Capped on-screen spell effects to keep frame rate stable during dense combat.
  • Faster login — Optimised the login/loading sequence and disabled the legacy updater.
  • Monster teleport lag fix — Removed a hitch when monsters teleport.
  • Smoother NPC/monster movement — The network catch-up that made monsters visibly “speed up / micro-teleport” now uses a continuous factor (+25% speed per queued step instead of abrupt ×2/×3 jumps) — ordinary monsters move smoothly again while dungeon waves still drain their backlog just as fast.
  • Game data memory-mapped — The data files (.dda sprites, world database) are now truly memory-mapped (they never were, despite the class name): reads are served by the OS page cache with no seek state, and the per-byte XOR decode now works per 4 KB block.

Stability, 64-bit & diagnostics

  • Crash minidumps — Any crash (or abnormal exit) now writes CrashDumps\T4CClient_<date>.dmp next to the exe plus a CRASH line in BootLog.txt — open the dump in Visual Studio to get the full call stacks of every thread.
  • 804 x64 warnings fixed — The 64-bit build is now warning-free. Among them, real x64 bugs: UDP completion-port packet pointers truncated to 32 bits (guaranteed corruption), the audio callback pointer likewise, and printf-format mismatches.
  • AddressSanitizer build — New opt-in asan64.cmd build that catches buffer overflows and use-after-free at runtime during test sessions.
  • Deprecated APIs retired — GetVersionEx and inet_addr replaced by supported equivalents; leftover debug logging removed from the mouse/render hot paths.

Input

  • DirectInput removed — Keyboard and mouse now use native Windows input (GetAsyncKeyState, WM_MOUSEWHEEL) instead of the DirectInput API deprecated since ~2005 — one less emulation layer, dinput8.dll no longer imported. Same keys, buttons, wheel direction and alt-tab behaviour.

HTML user interface (Ultralight)

  • Pre-game UI — New HTML front-end for login, character selection/creation, options and splash, driven by Ultralight over D3D11.
  • In-game character sheet — Live HTML character sheet overlay (Ctrl+S); fixed a black flash on open.
  • Inventory & equipment UI — New HTML inventory and equipment screens; right-click shows consumable (potion) effects.
  • NPC dialogue panel — Second Ultralight view: an HTML dialogue panel above the NPC with clickable keywords and free text input.
  • Login QoL — First character is selected by default on the login screen.

Audio

  • Removed MP3/CD music player — The old music players were polling constantly and tanking FPS; removed.
  • Sound rate cap — Limited sounds to ~20/second, recovering from 10 fps back to 54 fps in heavy scenes.
  • Floor-item sound fix — Stopped loading sound assets for ground items that don’t need them.
  • Distance-based sound (spatial) — Monster combat sounds (attacks, pain cries, deaths) now fade with distance from the player instead of always playing at full volume: full up to ~10 tiles, a smooth roll-off to a faint level by ~30 tiles, then silence beyond. The player’s own sounds and UI sounds are unaffected.
  • DirectShow removed (music playback) — Background music and cave/crypt ambience used a DirectShow “video” player just to decode MP3. Replaced by a modern audio path: Media Foundation decodes the MP3 and XAudio2 plays it with native looping and volume — all Windows SDK, nothing extra to ship. The old position-polling loop thread is gone (XAudio2 loops natively).

Lighting

  • Light / low-light fixes — Corrected light and low-light rendering.
  • Permanent night in caverns — Cavern dungeons now stay dark regardless of world time.

Chat & text

  • Paste crash fix — Fixed a random crash when pasting text (a thread race on the chat text sprite, now guarded by a per-object critical section).
  • Paste speed fix — Removed the O(n²) per-character rebuild and the hard-coded paste throttle; pasting is now instant.
  • Chat clipping under D3D11 — Long chat lines no longer overflow to the left; the clip rectangle is honoured on the GPU path.

“Vampire Survivors” dungeon mode

  • Perk choice popup — HTML 3-card perk picker shown at the end of a wave; respects the client’s selected language and shows perk level transitions.
  • Player freeze during choice — The player is frozen (mouse and keyboard/arrow movement) while the perk panel is open.
  • Cleave “slash” visual — A procedural elliptical shockwave ring is drawn under the player on a melee swing, sized to the cleave radius (grows with the perk level).
  • Instant monster death — Removed the old delay (≈500 ms) before a killed monster plays its death animation; corpses now appear immediately and in sync.
  • Projectile-accurate spells — Spell damage, the monster’s hurt cry and death now land when the projectile visually hits, not at cast time.
  • Projectile-accurate arrows — Arrows fly faster (tunable) and their impact — damage, the monster’s pain sound and death — is deferred to the moment the arrow lands.
  • Group-based PvP cursor (no combat mode) — Removed the Ctrl+C “combat mode” toggle. The attack cursor now shows by default when hovering another player who is not in your group; group members keep the neutral cursor. Safe zones need no special handling client-side — the server already blocks attacks there.

Network security

  • Encrypted & authenticated packets — On connect the client now runs an ECDH P-256 key exchange with the server and encrypts every UDP packet with AES-256-GCM — confidentiality, integrity and authenticity per packet — using native Windows CNG (bcrypt), no external dependency.
  • Anti-replay & anti-spoofing — Each packet carries a monotonic sequence (used as the GCM nonce) with a sliding replay window; a packet’s identity is bound to the session key, not the source address — so address spoofing and packet replay no longer work.
  • Crypto cost per packet cut ~50× (~10-50 µs → 0.6 µs) — The shared SecureChannel module no longer opens a bcrypt provider and generates an AES-GCM key on every packet: the provider is opened once and both directional key handles are derived once per session at the handshake. Same change on client and server (shared file); the wire format is untouched, so an un-patched client stays compatible.

SERVER Game server

Build & infrastructure

  • VS2022 toolset — Server and DLLs build on the VS2022 (v143) toolset.
  • 64-bit build — Server and all 8 NPC plugin DLLs build and run 64-bit.
  • x64 bug fixes — Truncated IOCP completion key and thread handle, and a wrong-size flag memcpy.
  • 1080p display range — Increased NPC/item view range and monster spawn distance for 1080p screens.

Localization & content fixes

  • Per-player language — Server messages now use each player’s language everywhere (fixes NPC lists previously stuck in English).
  • UTF-8 fix — Corrected UTF-8 handling.
  • Potion effects — Consumable use effects (HP/mana) are reported so the client can display them.
  • Evil-quest bug fix — Fixed a random bug in the evil quest line.
  • NPC purchase spam fix — NPCs no longer repeat the “thanks for your purchase” message.

Performance & stability

  • Deadlock-logging tracer disabled — The lock tracer was serialising every lock through one global section (~45% CPU); disabled in code.
  • Memory leak fix — Plugged a server memory leak.
  • Area-spell packet regrouping — Grouped per-target area-spell effects into one packet instead of a UDP burst that was being dropped (~85% loss).
  • Flag table fix — Fixed duplication / over-loading of the quest-flag table.
  • Faster startup — WDA data loading ~29% faster (≈375 ms → 265 ms measured) — Removed O(n²) work in WDA loading: unit-type name resolution (GetIDFromName, also the per-registration duplicate check) now uses a name→id index instead of a full linked-list scan; item appearances are cached instead of creating & destroying a full unit object 8× per monster; NPC script-item lookup uses an (id,type) map. World/map loading and the runtime spatial grid were already O(1) and unchanged (only a minor grid-init memset). Behaviour is identical — startup is just faster, scaling with the number of items/monsters/NPCs.
  • Collision map unpacked to 1 byte/cell — lock-free IsBlocking (8 threads: 165 ms → 1.8 ms per 400k lookups) — The collision map was stored 4 bits per cell (two cells per byte). That packing is what forced the world lock: SetBlocking had to read-modify-write a byte shared by two cells, so two threads writing neighbouring cells could corrupt each other — which meant IsBlocking had to take the map lock just to read one cell. Measured on the real map, that lock serialised every thread: going from 1 to 8 threads made the server 33× slower (4.97 ms → 165 ms), i.e. adding cores actively hurt. Cells are now unpacked to 1 byte at load, so writing a cell is an atomic x86 store and IsBlocking reads with no lock at all — 8 threads now cost 1.8 ms and scaling is flat instead of collapsing. Also fixed on the way: a delete on a new[], a map name not NUL-terminated (std::string read past the stack buffer), and a bounds guard whose arithmetic overflowed before the check ran. The on-disk format is unchanged (still 4 bits/cell — nothing to regenerate). The previous memory-mapped “pristine” trick is therefore gone: map memory rises from ~47 MB to ~170 MB resident — a deliberate trade, RAM for the lock. Equivalence was proven cell by cell across all 8 worlds: 75,497,472 cells, zero divergence.
  • Tile-deduplicated map format — measured, then rejected — Kept for the record: the map was also tested as an 8×8 deduplicated tile format (36 MB → 3.9 MB on disk, table small enough for L2). Benchmarked against the real access patterns it was slower, not faster — 2.09× on the pathfinding flow field, 1.19× on clustered collision checks — because accesses are spatially clustered and already sit in cache; the indirection only added work. It only won (1.04×) on fully scattered lookups, which the server never does. The flat format was the right one all along; the lock was the problem.
  • Database ODBC → MySQL — Replaced ODBC — which serialised all database access through one global lock and one write thread — with a direct libmariadb backend; connection settings moved to MYSQL_* keys in T4CServer.ini.
  • Bulk autosave — All connected players are saved in a few SQL commands per tick instead of ~1800; one write connection with a deadlock retry and a capped transaction size.
  • Mass-disconnect RAM leak fixed — Lost connections were freed at only ~10/s (a Sleep(100) each), ballooning RAM until crash; now drained in bulk.

Network throughput — 1800 concurrent players, no lag (validated)

  • Broadcast worker pool unthrottled — 8 → 31 workers (~57k → ~130-260k sends/s) — The biggest win by far. BCAST_POOL_MAX was hard-coded to 8 regardless of core count. Broadcast throughput is exactly workers ÷ per-send latency, so on a 32-core machine the pool was capped at ~57k sends/s while 500 players in one area need ~130k/s — the queue filled and dropped broadcasts, delivering stale positions (rubber-banding). Now one worker per core; the send-thread pool was capped at 7 for the same reason and is now 15 (its array was resized accordingly).
  • AES key no longer regenerated per packet (~10-50 µs → 0.6 µs per seal) — Every sealed packet opened a fresh bcrypt provider and generated a new AES-GCM key, then destroyed both — ~175k times per second. The provider is now opened once, and the two directional key handles are generated once per session at the ECDH handshake and cached in the session. Wire format unchanged, so old clients stay compatible.
  • Connection table sharded (32 ways) — The GetConnection hot path (~173k lookups/s) funnelled every send, receive and maintenance pass through a single lock. The table is now 32 independent shards (Fibonacci-hashed on the connection key), each with its own critical section, and the maintenance pass locks one shard at a time instead of freezing the whole table for 5-50 ms every 100 ms. Earlier reader/writer-lock attempts caused livelocks; sharding removes the single hot lock entirely.
  • Broadcast convoy removed (92 µs → 0.1 µs per send) — Concurrent broadcast jobs carry near-identical recipient lists (the same nearby players), so every worker walked the list from index 0 at the same instant and piled up on each connection's send lock in lockstep — ~30 workers queueing on one lock. Each job now enters the list at a rotating offset, so workers touch distinct connections at any instant.
  • Lock-free UDP packet pool — Once crypto was fast, PacketAlloc/PacketFree churned the CRT heap ~260k times/s and became the bottleneck (live packets peaked at 290k). Packets ≤2 KB are now recycled with their buffer through a Windows SLIST (lock-free, ABA-safe); larger split packets still use the heap. Note: a first attempt using a single critical section was worse than the heap on 32 cores — the CRT's low-fragmentation heap has per-core arenas, one global lock does not.
  • Result — 500 concurrent players in a single area: zero dropped broadcasts, broadcast queue drained (12/4000), no rubber-banding, no perceptible lag. The complete send path — shard lock, connection lock, AES-GCM seal, packet allocation and IOCP post — measures ~5 µs end to end.
  • 1800 concurrent players — The server sustains 1800 players at once with no lag in steady state (load-tested).
  • Anti-flood: private ranges exempt — The per-IP connection cap (16 simultaneous) blocked load testing from a single LAN host. Loopback and the RFC1918 private ranges (10/8, 172.16/12, 192.168/16) are now exempt; the cap and the creation rate-limit stay fully enforced for public IPs — a flood cannot originate from ranges that are not routable on the Internet.
  • Temporary profilers removed — The instrumentation that located all of the above ended up being a bottleneck itself: it printed to the console from the packet-processing thread, and Windows console I/O is synchronous and serialised — it stalled that thread for up to 1.3 s, showing up in-game as a 1-2 s input delay. All profiling code has been removed from the hot paths.

Bandwidth — move broadcasts grouped (written, not yet built)

  • Where the bytes actually go — A move broadcast costs 83 bytes on the wire to carry 8 bytes of real change (unit id + X + Y) — 90% overhead. The breakdown matters: 28 IP/UDP + 4 PacketHeader + 24 AES-GCM seal = 56 bytes of per-datagram framing, then 4 dead bytes + 6 (id/X/Y) + 17 of full unit description. The framing is the point: shrinking the payload cannot touch it. Measured on the 500-clustered-bot scenario, movement alone accounts for ~415 Mbps (500 players × 2.5 broadcasts/s × ~500 recipients × 83 B) — the fanout is O(n²) in a dense crowd.
  • Megapack revived — 83 → 31 bytes per move (~415 → ~154 Mbps) — Since only fewer/bigger datagrams can amortise the 56-byte framing, small unreliable packets are grouped again. The transport already had a “megapack” mechanism but it had been dead since encryption landed: packets were sealed before the grouping decision, and the code then forced bSendDirect on anything sealed — so nothing could ever be grouped (and EnableCOMMMegaPack was 0 in the ini besides). Grouping now happens before the seal and the whole megapack is sealed once — which is exactly what the client already expects, since it unseals the datagram and then looks for the 0xFFFF marker in the plaintext. No client change required. Up to 33 moves per datagram → 31 B/move.
  • Megapack no longer forced reliable — The old grouping code set ushNeedAck=1 / ulNbrAck=2 on every megapack. Applied to movement that is a contradiction: it would retransmit stale positions — worse than dropping them, and extra traffic while trying to remove some. Move megapacks are now unreliable, matching the packets they carry.
  • Trade-off — Grouping adds up to MEGA_FLUSH_MS (20 ms) before a datagram leaves, including the echo of the player’s own move (the sender is not excluded from the broadcast) — ~10% of the 200 ms move step. Under load the megapack fills on size well before the timer, so the delay mostly bounds low-traffic connections. Requires EnableCOMMMegaPack=1 in T4CServer.ini (it ships at 0) — which is also the kill switch: set it back to 0 to restore immediate sends.
  • Status — The wire format is validated by an independent round-trip bench: 200 moves built exactly as the server builds them, then parsed exactly as the client parses them — 7 datagrams, all 200 sub-packets recovered with correct content and order, 31.1 B/move. The server itself has not been compiled (the MFC component is missing from the local Visual Studio install), so this is not yet a shipped, run-tested change. The ~154 Mbps figure is computed from verified packet sizes, not measured on a live run.
  • Next (not done) — Slimming the packet itself — dropping the 4 dead bytes (a key/checksum header that is written as zeros and never filled: the encryption it belonged to is commented out on both sides) and sending only what changes instead of the full 17-byte unit description — takes it further, to ~13 B/move (~64 Mbps). It is deliberately not bundled here: it changes the shared wire format on every packet in the game, needs a client redeploy, and has no ini kill switch. Sequenced after the megapack is built and verified, so that a regression has one suspect instead of two.

Dungeon & monster waves

  • New isolated world — A dedicated world for the Vampire-Survivors mode.
  • Wave system — Monster wave spawning with sub-waves, aggro circles and tuned spawn distances.
  • Multiple monster types per wave — A wave can mix monster types by percentage (e.g. goblin(50) bat(25) rat(25)).
  • Dungeon mapping & commands — Flood-fill dungeon detection with a size filter, plus DUNGEONID, MAPDUNGEONS and TPDUNGEON (teleport to a dungeon’s nearest walkable centre).

Perk system

  • Player-chosen perks — Transient per-run perks offered at wave end (server picks 3, client shows the cards, choice returns to the server); cleared on death, disconnect or dungeon completion.
  • Upgradeable perks — Re-picking a perk levels it up; effects scale per level.
  • Multi-target spells — Single-target spells splash to nearby monsters; the count grows with the perk level.
  • Spell power & magic lifesteal — Increased spell damage and life-on-damage healing, both scaling with level.
  • Melee cleave — Melee auto-attacks become an area hit (radius grows with level), melee weapons only — not bows.
  • Freeze during selection — The current dungeon (player, group and its monsters, plus the wave timer) is frozen while a perk is being chosen.

Combat — projectile-accurate impact

  • Ghost-monster fix (root cause) — Creatures::Death now broadcasts the corpse for every death, so indirectly-killed monsters (cleave, area spells, DoT) no longer stay shown alive on the client.
  • Deferred spell impact — Spell damage/death/loot are applied when the projectile reaches the target; the flight time is computed to match the client projectile exactly, with no protocol change.
  • Deferred arrow impact — Bow arrows behave like spells: the arrow flies first, then damage and death are applied on arrival.
  • Arrow HP-bar sync — On arrow impact the server broadcasts a unit update (same mechanism as spells) so the monster’s health bar drops on hit instead of one shot late.
  • Cleave slash broadcast — New lightweight packet so nearby clients can draw the melee cleave shockwave.
  • Group-based PvP (no more combat mode) — Removed the “combat mode” (Ctrl+C) requirement for offensive spells. In any PvP-capable (unprotected) zone, offensive spells — single-target and area — now hit any player who is not in your group; group members are never hit, and safe havens remain fully protected. This also fixes area spells being wrongly rejected with “You cannot cast offensive spells on yourself.” when no monster was targeted (the target resolved to the caster). A single-target offensive spell on yourself is still blocked; an area spell centred on yourself is allowed.

Network security

  • Encrypted & authenticated UDP protocol — The server answers the client’s ECDH P-256 handshake, derives a per-session key (HKDF) and encrypts/authenticates every packet with AES-256-GCM, all via native Windows CNG (bcrypt) — no external dependency. Built into the transport layer, so no application code changed.
  • Identity bound to the session key — A packet is now attributed to a player by verifying its authentication tag, not by its source UDP address — closing the long-standing address-spoofing and replay weakness of the address-based protocol. Anti-replay uses a per-session sliding sequence window.
